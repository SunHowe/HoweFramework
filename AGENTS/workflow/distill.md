# 任务结束沉淀协议

根 [`AGENTS.md`](../../AGENTS.md) 只放检查清单。本文件是判定与落盘细则。

每次非纯问答任务结束后**必须**走完本节。纯问答、只读搜索且没有新结论，可以在收尾里写「无需沉淀」。

## 何时必须写 Doc

命中任一条 → 更新或新建 `Doc/` 下的 md：

1. **契约**：公共 API、模块生命周期、请求/事件/表结构对调用方可见的行为变了。
2. **约定**：命名、分层、扩展方式（何时加 Module / Manager / Component）有新增或修正。
3. **取舍**：在两个可行方案里选了 A 不选 B，且后人还会碰到同一选择。
4. **坑**：非显而易见的约束（销毁顺序、必须 Dispose、枚举占用区间、线程/生命周期限制）。
5. **流程**：可重复的操作步骤（如何加 UI、如何加协议、如何加组件、如何出表）。

## 何时不要写

- 一次性修 bug，没有普遍教训。
- 聊天过程、尝试路径、会话纪要。
- 未实现的设计、规划、RPG/玩法脑暴。
- 把源码注释或方法列表复制进 md。
- 在 `Client/Assets/**/Doc` 或框架长 README 里写第二份知识。

## 写到哪

1. 打开 [`Doc/README.md`](../../Doc/README.md) 按「先读哪篇」找家。
2. **有对应文件就改旧文**，不要平行再开一篇同题文档。
3. 没有家才在最贴近的子目录新建 md，文件名用短英文短横线（与现有 `event.md`、`entity-component.md` 一致）。
4. 模块手册用下面模板。架构/规范/流程类按该目录已有篇章结构对齐。

### 模块文档模板

```markdown
# 模块名

## 职责

## 关键类型

## 用法

## 扩展点

## 约束与坑

## 相关源码
```

每条用法和结论必须能指向具体源码路径（仓库相对路径）。禁止凭记忆或已删除的旧 Doc 编写。

## 写完立刻维护索引

按 [`index-maintenance.md`](index-maintenance.md)：新文件或改名/删除 → 所在目录 `README.md` → 父目录 README → 直到 `Doc/README.md`。

若本次改的是 agent 工作方式（本目录、`AGENTS/domains/`、根 `AGENTS.md`），同样更新 `AGENTS/` 索引；根文件的开工/完成清单变了才改 [`AGENTS.md`](../../AGENTS.md)。

## 收尾时要交代

在给用户的最终回复里用一两句说明：沉淀了哪篇、或为何无需沉淀。
